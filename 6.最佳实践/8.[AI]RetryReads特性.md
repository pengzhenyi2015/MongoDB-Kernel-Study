## 1. 概述

### 1.1 什么是 Retryable Reads

Retryable Reads（可重试读）是 MongoDB 3.6+ 引入、并在 4.2 中完善的读操作韧性机制。当一次读操作因**瞬时网络错误**或**主节点切换**等原因失败时，驱动会自动选择新服务器并重试，对应用层透明，从而显著提升面对短暂故障时的 resilience。

**核心特征**：

| 维度 | 说明 |
|------|------|
| **默认状态** | 驱动端默认开启（`retryReads=true`） |
| **重试上限** | 普通场景下只重试 **1 次**；CSOT 模式（设置了 Client 级 Timeout）下可在上下文截止前无限重试 |
| **幂等保证** | 读天然幂等，不需要事务号去重（与 retryable writes 的关键区别） |
| **部署要求** | 无特殊要求（副本集、分片集群、Standalone 均可） |
| **getMore 限制** | `getMore` **不可重试**——无法判断游标是否已前进 |

### 1.2 retryable reads 与 retryable writes 的本质区别

| 维度 | retryable reads | retryable writes |
|------|----------------|-----------------|
| **实现层** | 纯驱动层行为 | 驱动层 + 服务端协作 |
| **服务端选项** | 服务端不解析 `retryReads` | 服务端解析 `retryWrites` |
| **服务端错误标签** | 无 `RetryableReadError` 标签 | 有 `RetryableWriteError` 标签 |
| **幂等保证** | 读天然幂等，无需事务号 | 依赖 `lsid` + `txnNumber`，服务端通过 oplog 去重 |
| **重试判定** | 驱动依据错误码 + `NetworkError` 标签 | 4.4+ 信任服务端 `RetryableWriteError` 标签 |

### 1.3 双端协作模型

与 retryable writes 不同，retryable reads 的重试逻辑**几乎完全在驱动端**完成。服务端提供的是通用的"可重试错误"基础设施，而非专门为读重试设计的机制。

```
┌─────────────────────────────────────────────────────────────────────┐
│                         驱动端 (Driver)                              │
│                                                                     │
│  1. 解析 retryReads=true 配置                                       │
│  2. 为读操作分配 RetryMode (RetryOncePerCommand)                    │
│  3. 首轮判定 retrySupported（事务内=false）                          │
│  4. 收到错误后调用 RetryableRead() 判定是否可重试                     │
│  5. 重试时选择新服务器（降权失败服务器）                              │
│  6. 连接池被清空也触发重试                                           │
└────────────────────────────┬────────────────────────────────────────┘
                             │  读命令（无需 txnNumber）
                             ▼
┌─────────────────────────────────────────────────────────────────────┐
│                       服务端 (Server)                                │
│                                                                     │
│  1. 执行读操作                                                       │
│  2. 返回结果 或 返回带可重试错误码的错误                              │
│  3. mongos 内部提供多层重试（ARS、ShardRemote）                      │
│  4. snapshot 读：mongos 可重新选择 atClusterTime 重试                 │
│  5. partialResultsReturned：分片部分故障时返回部分结果                │
│  注：服务端不附加 RetryableReadError 标签，                           │
│      驱动依据错误码自行判定                                          │
└─────────────────────────────────────────────────────────────────────┘
```

## 2. 使用场景

### 2.1 适用场景

| 场景 | 典型错误 | 重试效果 |
|------|---------|---------|
| **副本集主节点切换** | `NotWritablePrimary`(10107)、`PrimarySteppedDown`(189)、`InterruptedDueToReplStateChange`(11602) | 等待新主就绪后在新主上成功 |
| **瞬时网络故障** | `HostUnreachable`(6)、`HostNotFound`(7)、`NetworkTimeout`(89)、`SocketException`(9001) | 自动重连并重试 |
| **服务端关闭中** | `ShutdownInProgress`(91)、`InterruptedAtShutdown`(11600) | 切换到健康节点重试 |
| **mongos 抖动** | mongos 到 shard 连接异常 | 驱动重选 mongos 或 mongos 内部重试 |
| **多数提交读不可用** | `ReadConcernMajorityNotAvailableYet`(134) | 等待 majority commit 可用后重试 |
| **服务端过载** | `SystemOverloadedError` | 配合 `MaxAdaptiveRetries` 带退避重试 |
| **连接池被清空** | `poolClearedError` | 驱动自动重试获取连接 |

### 2.2 不适用 / 不生效的场景

| 场景 | 原因 |
|------|------|
| **`getMore`** | 无法判断游标是否已前进，驱动不会自动重试 |
| **事务内的读操作** | `retryable()` 对事务内读返回 false |
| **`RunCommand`** | 不设置 `Type` 和 `RetryMode`，不参与重试 |
| **带 `$out`/`$merge` 的 aggregate** | 本质是写操作，会关闭读重试 |
| **业务需要精确控制重试** | 可关闭 retryReads 并自定义重试逻辑 |

## 3. 支持的操作范围

### 3.1 驱动端视角（mongo-go-driver）

| 操作 | 可重试 | RetryMode | 备注 |
|------|--------|-----------|------|
| `Find` / `FindOne` | ✅ | `RetryOncePerCommand` | 核心读操作 |
| `Aggregate`（不含 `$out`/`$merge`） | ✅ | `RetryOncePerCommand` | 含写阶段时关闭 |
| `Distinct` | ✅ | `RetryOncePerCommand` | 幂等 |
| `CountDocuments` / `EstimatedDocumentCount` | ✅ | `RetryOncePerCommand` | 幂等 |
| `ListDatabases` / `ListCollections` / `ListIndexes` | ✅ | `RetryOncePerCommand` | 元数据读 |
| Change Streams | ✅ | 独立计数器 | 使用独立的 retries 逻辑 |
| `getMore` | ❌ | 不重试 | 游标位置不可知 |
| `RunCommand` | ❌ | 不参与 | 不设置 Type/RetryMode |

### 3.2 服务端视角（MongoDB 8.0）

## 4. 配置与使用方式

### 4.1 连接字符串

```
mongodb://host:port/db?retryReads=true
```

### 4.2 Go 驱动配置

**Options API**：

```go
// mongo/options/clientoptions.go
// SetRetryReads specifies whether supported read operations should be retried once on certain errors...
// The default is true.
func (c *ClientOptions) SetRetryReads(b bool) *ClientOptions {
    c.RetryReads = &b
    return c
}
```

**Client 初始化**（默认开启）：

```go
// mongo/client.go
client.retryReads = true
if clientOpts.RetryReads != nil {
    client.retryReads = *clientOpts.RetryReads
}
```

### 4.3 使用示例（Go）

```go
// 默认开启，无需额外配置
client, err := mongo.Connect(context.TODO(),
    options.Client().ApplyURI("mongodb://localhost:27017"))
coll := client.Database("test").Collection("docs")

// 以下读操作若遇瞬时错误会自动重试一次
cur, err := coll.Find(context.TODO(), bson.D{{"v", 1}})
```

### 4.4 CSOT 模式（无限重试直到超时）

```go
opts := options.Client().
    ApplyURI("mongodb://localhost:27017").
    SetTimeout(30 * time.Second) // 设置 Client 级 Timeout → CSOT 模式
// retry reads 会在 30s 截止前持续重试，而非仅 1 次
```

### 4.5 关闭 retryReads

```go
// 通过连接字符串
uri := "mongodb://localhost:27017/?retryReads=false"

// 或通过 Options API
opts := options.Client().ApplyURI("mongodb://localhost:27017").SetRetryReads(false)
```

## 5. 驱动端实现原理（mongo-go-driver）

### 5.1 核心类型：RetryMode 与 Type

`x/mongo/driver/driver.go` 定义了驱动内部描述操作类型与重试策略的基础类型：

```go
type Type uint

const (
    _ Type = iota
    Write
    Read
)

type RetryMode uint

const (
    RetryNone RetryMode = iota          // 不重试
    RetryOnce                           // 整个操作重试一次
    RetryOncePerCommand                 // 每个分批命令各重试一次
    RetryContext                        // 重试直到 context 截止
)

func (rm RetryMode) Enabled() bool {
    return rm == RetryOnce || rm == RetryOncePerCommand || rm == RetryContext
}
```

- 读操作被标记为 `Type: Read`。
- 上层读 API 普遍使用 `RetryOncePerCommand`（对每个下发到服务端的命令各给 1 次重试机会）。
- 少数操作（如带 `$out` 的 aggregate）会切换类型为 `Write`。

### 5.2 各读操作的 Wiring

以 `mongo/collection.go` 的 `Aggregate` 为例：

```go
retry := driver.RetryNone
if coll.client.retryReads {
    retry = driver.RetryOncePerCommand
}

op := operation.NewAggregate(pipelineArr).
    Retry(retry).                       // 注入重试模式
    MaxAdaptiveRetries(maxAdaptiveRetries).
    EnableOverloadRetargeting(coll.client.enableOverloadRetargeting).
    ...
```

**关键限制**：
- 带 `$out`/`$merge` 的 aggregate 会关闭重试：`retryReads := a.client.retryReads && !hasOutputStage`，因为这类操作本质是写。
- `RunCommand` 不设置 `Type` 和 `RetryMode`，因此永远不会走重试路径。

各读操作的文件位置：

| 操作 | 文件 |
|------|------|
| Find / FindOne | `x/mongo/driver/operation/find.go` |
| Aggregate | `x/mongo/driver/operation/aggregate.go` |
| Count / CountDocuments | `x/mongo/driver/operation/count.go` |
| Distinct | `x/mongo/driver/operation/distinct.go` |
| ListDatabases | `x/mongo/driver/operation/list_databases.go` |
| ListCollections | `x/mongo/driver/operation/list_collections.go` |
| ListIndexes | `x/mongo/driver/operation/list_indexes.go` |
| Change Streams | `mongo/change_stream.go`（独立 retries 计数器） |

### 5.3 核心状态机：Operation.Execute

`x/mongo/driver/operation.go` 的 `func (op Operation) Execute(ctx context.Context) error` 是整个重试逻辑的中枢。

#### 5.3.1 计算重试预算

```go
defaultRetries := ptrutil.Ptr(uint(0))
if op.RetryMode != nil {
    switch op.Type {
    case Read:
        switch *op.RetryMode {
        case RetryOnce, RetryOncePerCommand:
            defaultRetries = ptrutil.Ptr(uint(1))   // 读：1 次
        case RetryContext:
            defaultRetries = nil                     // 无限
        }
    }
    // CSOT 模式：只要启用了重试就改为无限重试
    if csot.IsTimeoutContext(ctx) && op.RetryMode.Enabled() {
        defaultRetries = nil
    }
}
```

- 普通读：`RetryOncePerCommand` → 预算为 **1**。
- CSOT（Client 设了 `Timeout`）：预算变为 `nil`，即在 context 截止前**不限次数**重试。

#### 5.3.2 每轮循环携带的状态

```go
var srvr Server
var conn *mnet.Connection
var prevErr error
var attempt uint
retrySupported := false
first := true
var deprioritizedServers []description.Server  // 累积要降权的服务器
```

`deprioritizedServers` 会跨重试累积，避免反复选中刚刚失败的服务器。

#### 5.3.3 首轮才判定的 retrySupported

```go
if first {
    retrySupported = op.retryable(conn.Description())   // 读：事务内不可重试
    first = false
}
```

`retryable()` 依据首个服务器的描述判断该操作是否支持重试——读操作在事务内执行时不支持重试。该判定**只做一次**，不会因换服务器而重新评估。

#### 5.3.4 错误分类与重试决策

```go
} else {
    retryableErr = tt.RetryableRead()   // 读：调用错误分类
}
olRetryErr := tt.HasErrorLabel(ErrRetryableError) && isOverloadedError
needRetry := (retrySupported && retryEnabled && retryableErr) ||
    (op.MaxAdaptiveRetries != 0 && olRetryErr)

if needRetry && (allowedRetries == nil || attempt < *allowedRetries) {
    ...
    if err = resetForRetry(tt); err != nil { return err }
    continue
}
```

触发重试需要同时满足：`retrySupported`（首轮判定支持）+ `retryEnabled`（用户开启）+ `retryableErr`（错误可重试）+ 剩余重试次数（`nil` 表示无限）。

#### 5.3.5 resetForRetry：重试前的状态复位

```go
resetForRetry := func(err error) error {
    attempt++
    prevErr = err
    ...
    if conn != nil {
        // 分片拓扑或开了 overload retargeting 时，把失败服务器加入降权列表
        if op.Deployment.Kind() == description.TopologyKindSharded ||
            (isOverloadedError && op.EnableOverloadRetargeting) {
            deprioritizedServers = append(deprioritizedServers, conn.Description())
        }
        conn.Close()
    }
    srvr = nil   // 强制下一轮重新选服务器
    conn = nil   // 强制下一轮重新获取连接
    // 仅对 overload 错误做指数退避 + 抖动
    if isOverloadedError { ... 指数退避 100ms~10s ... }
    return nil
}
```

退避常量：`backoffInitial = 100ms`，`backoffMax = 10s`。**普通网络错误不退避**，立即重试；只有 `SystemOverloadedError` 才走指数退避。

#### 5.3.6 连接池错误的重试

```go
if srvr == nil || conn == nil {
    srvr, conn, err = op.getServerAndConnection(ctx, requestID, deprioritizedServers)
    if err != nil {
        // 连接池被清空等可重试的池错误
        if rerr, ok := err.(RetryablePoolError); ok && rerr.Retryable() &&
            (allowedRetries == nil || attempt < *allowedRetries) {
            if err = resetForRetry(err); err != nil { return err }
            continue
        }
        if prevErr != nil { return prevErr }
        return err
    }
}
```

`poolClearedError` 实现了 `RetryablePoolError` 接口，因此**连接池被清空**也会触发重试。

### 5.4 错误分类：哪些读错误会重试

`x/mongo/driver/errors.go` 的 `RetryableRead()` 是读侧判定的核心：

```go
func (e Error) RetryableRead() bool {
    for _, label := range e.Labels {
        if label == NetworkError {       // 任何带 NetworkError 标签 → 可重试
            return true
        }
    }
    for _, code := range retryableCodes { // 错误码命中 → 可重试
        if e.Code == code {
            return true
        }
    }
    return false
}
```

**可重试错误码列表**：

```go
retryableCodes = []int32{
    6,     // HostUnreachable
    7,     // HostNotFound
    89,    // NetworkTimeout
    91,    // ShutdownInProgress
    134,   // ReadConcernMajorityNotAvailableYet
    189,   // PrimarySteppedDown
    262,   // ExceededTimeLimit
    9001,  // SocketException
    10107, // NotWritablePrimary
    11600, // InterruptedAtShutdown
    11602, // InterruptedDueToReplStateChange
    13435, // NotPrimaryNoSecondaryOk
    13436, // NotPrimaryOrSecondary
}
```

**网络错误的标签化**：底层传输错误会通过 `networkError()` 被包装并自动打上 `NetworkError` 标签，使得原始的连接断开、读写超时等也能命中 `RetryableRead()`。

**与 retryable writes 错误判定的区别**：
- 读重试：完全依赖错误码 + `NetworkError` 标签，**不依赖服务端附加的标签**。
- 写重试：4.4+ 完全信任服务端 `RetryableWriteError` 标签。

### 5.5 重试时的服务器选择

`selectServer` 会把用户的选择器包裹进 `Deprioritized` 选择器，跳过累积的失败服务器：

```go
deprioritizedSelector := serverselector.NewDeprioritized(selector, deprioritized)
return op.Deployment.SelectServer(ctx, deprioritizedSelector)
```

因此重试时驱动会**优先选择不同的服务器**（分片拓扑或开了 overload retargeting 时），提高成功率。

### 5.6 过载重试（自适应重试）

`SystemOverloadedError`（服务端过载标签）配合 `ErrRetryableError` 标签和 `MaxAdaptiveRetries` 预算，构成独立于普通重试的**自适应过载重试**通道，并启用指数退避（100ms~10s）。

## 6. 服务端实现原理（MongoDB 8.0）

### 6.1 为什么说 retryReads 是驱动层行为

服务端 `mongo_uri.cpp` 只解析 `retryWrites`，**不解析** `retryReads`：

```cpp
// src/mongo/client/mongo_uri.cpp:493-532
auto extractBooleanOption =
    [&options](CaseInsensitiveString optionName) -> boost::optional<bool> { ... };

const auto retryWrites = extractBooleanOption("retryWrites");
// 注意：这里只解析了 retryWrites，没有解析 retryReads！
```

服务端 `MongoURI` 类**没有** `_retryReads` 字段。Shell 的 `SessionOptions` 同样只有 `retryWrites`。

错误标签机制也只服务于写/事务——服务端**不存在** `RetryableReadError` 标签。驱动是根据错误码本身判断是否可重试。

### 6.2 可重试错误码分类：RetriableError

驱动判断"是否可重试"的依据是错误码是否属于 `RetriableError` 分类。服务端在 `src/mongo/base/error_codes.yml` 中定义：

```yaml
- {code: 6,   name: HostUnreachable,        categories: [NetworkError, RetriableError]}
- {code: 7,   name: HostNotFound,           categories: [NetworkError, RetriableError]}
- {code: 89,  name: NetworkTimeout,         categories: [NetworkError, RetriableError, NetworkTimeoutError]}
- {code: 91,  name: ShutdownInProgress,     categories: [ShutdownError, CancellationError, RetriableError]}
- {code: 134, name: ReadConcernMajorityNotAvailableYet, categories: [RetriableError]}
- {code: 189, name: PrimarySteppedDown,     categories: [NotPrimaryError, RetriableError]}
- {code: 262, name: ExceededTimeLimit,      categories: [Interruption, ExceededTimeLimitError, RetriableError]}
- {code: 9001,name: SocketException,        categories: [NetworkError, RetriableError]}
- {code: 10107,name: NotWritablePrimary,    categories: [NotPrimaryError, RetriableError]}
- {code: 11600,name: InterruptedAtShutdown, categories: [Interruption, ShutdownError, CancellationError, RetriableError]}
- {code: 11602,name: InterruptedDueToReplStateChange, categories: [Interruption, NotPrimaryError, RetriableError]}
- {code: 13435,name: NotPrimaryNoSecondaryOk, categories: [NotPrimaryError, RetriableError]}
- {code: 13436,name: NotPrimaryOrSecondary,    categories: [NotPrimaryError, RetriableError]}
```

### 6.3 服务端基础设施一：mongos → shard 的内部重试（AsyncRequestsSender）

mongos 在执行分片读时，通过 `AsyncRequestsSender` 向多个分片并发发命令。它对每个 host 有独立的失败重试计数，上限为 3：

```cpp
// src/mongo/s/async_requests_sender.cpp:69-70
// Maximum number of retries for network and replication NotPrimary errors (per host).
const int kMaxNumFailedHostRetryAttempts = 3;
```

当某个 shard 返回可重试错误时，ARS 会重新调度请求：

```cpp
// src/mongo/s/async_requests_sender.cpp:358-374
bool isStartingTransaction = _cmdObj.getField("startTransaction").booleanSafe();
if (!_ars->_stopRetrying &&
    shard->isRetriableError(status.code(), _ars->_retryPolicy) &&
    _retryCount < kMaxNumFailedHostRetryAttempts && !isStartingTransaction) {

    LOGV2_DEBUG(4615637, 1,
                "Command to remote shard failed with retryable error and will be retried",
                "shardId"_attr = _shardId,
                "error"_attr = redact(status));
    ++_retryCount;
    _shardHostAndPort.reset();
    return scheduleRequest();
}
```

注意：这是 **mongos 内部** 的重试，对客户端透明。即使驱动不重试，mongos 也会尽力把请求送达。

### 6.4 服务端基础设施二：ShardRemote 的命令重试

`Shard::runCommand` 是 mongos 向单个 shard 发命令的入口，内部是一个 `while(true)` 循环：

```cpp
// src/mongo/s/client/shard.cpp:165-191
StatusWith<Shard::CommandResponse> Shard::runCommand(OperationContext* opCtx,
                                                     const ReadPreferenceSetting& readPref,
                                                     const DatabaseName& dbName,
                                                     const BSONObj& cmdObj,
                                                     Milliseconds maxTimeMSOverride,
                                                     RetryPolicy retryPolicy) {
    while (true) {
        auto interruptStatus = opCtx->checkForInterruptNoAssert();
        if (!interruptStatus.isOK()) {
            return interruptStatus;
        }

        auto swResponse = _runCommand(opCtx, readPref, dbName, maxTimeMSOverride, cmdObj);
        auto status = CommandResponse::getEffectiveStatus(swResponse);
        if (isRetriableError(status.code(), retryPolicy)) {
            LOGV2_DEBUG(22719, 2,
                        "Command failed with retryable error and will be retried",
                        "command"_attr = redact(cmdObj),
                        "error"_attr = redact(status));
            continue;
        }

        return swResponse;
    }
}
```

重试策略通过 `RetryPolicy` 枚举控制：

```cpp
// src/mongo/s/client/shard.cpp:130-155
bool Shard::remoteIsRetriableError(ErrorCodes::Error code, RetryPolicy options) {
    switch (options) {
        case RetryPolicy::kNoRetry:
            return false;
        case RetryPolicy::kIdempotent:           // 读命令通常使用此策略
            return isMongosRetriableError(code); // 所有 RetriableError 都重试
        case RetryPolicy::kIdempotentOrCursorInvalidated:
            return remoteIsRetriableError(code, RetryPolicy::kIdempotent) ||
                ErrorCodes::isCursorInvalidatedError(code);
        case RetryPolicy::kNotIdempotent:
            return ErrorCodes::isNotPrimaryError(code);
    }
}
```

读命令通常使用 `kIdempotent` 策略（因为读天然幂等），所以所有 `RetriableError` 都会触发重试。

### 6.5 服务端基础设施三：ClusterFind 的查询级重试

`ClusterFind::runQuery` 对 `StaleConfig` / `StaleDbVersion` / `SnapshotError` 有专门的循环重试逻辑：

```cpp
// src/mongo/s/query/cluster_find.cpp:765-800
if (auto txnRouter = TransactionRouter::get(opCtx)) {
    if (!txnRouter.canContinueOnStaleShardOrDbError(kFindCmdName, ex.toStatus())) {
        throw;
    }
    // Reset the default global read timestamp so the retry's routing table reflects the
    // chunk placement after the refresh.
    txnRouter.onStaleShardOrDbError(opCtx, kFindCmdName, ex.toStatus());
    txnRouter.setDefaultAtClusterTime(opCtx);
}

} catch (DBException& ex) {
    if (retries >= kMaxRetries) {
        ex.addContext(str::stream() << "Failed to run query after " << kMaxRetries << " retries");
        throw;
    }
    if (ErrorCodes::isRetriableError(ex.code())) {
        ex.addContext("Encountered retryable error during query");
    } else {
        ex.addContext("Encountered non-retryable error during query");
    }
    throw;
}
```

### 6.6 服务端基础设施四：partialResultsReturned 容错

当查询设置了 `allowPartialResults: true`，mongos 在建立游标时遇到分片级别的可重试错误会**吞掉错误**并标记为部分结果：

```cpp
// src/mongo/s/query/establish_cursors.cpp:387-411

    bool isEligibleException = (isMongosRetriableError(status.code()) ||
                                status.code() == ErrorCodes::FailedToSatisfyReadPreference ||
                                status.code() == ErrorCodes::MaxTimeMSExpired);
    if (_allowPartialResults && isEligibleException) {
        // This exception is eligible to be swallowed.
        _remoteCursors.push_back({..., true /* partialResultsReturned */});
        return true;
    }
    return false;
}
```

## 8. snapshot 读场景深度分析

### 8.1 问题描述

客户端发起 `readConcern: {level: "snapshot"}` 的读，但所选的 `atClusterTime` 在某个 shard 上已被覆盖（快照窗口外），shard 返回 `SnapshotError`。

### 8.2 解决方式取决于 atClusterTime 的来源

#### A. 服务端自动选择 atClusterTime（客户端未提供）

mongos 会重新选择一个更晚的时间戳并重试。测试文件 `jstests/sharding/non_transaction_snapshot_errors.js:1-9` 说明：

```
Test that mongos retries SnapshotErrors for non-transaction snapshot reads with no client-
provided atClusterTime the same as it does for reads in multi-document transactions, but does
*not* retry them if the client provides atClusterTime.

In other words: If the client sends readConcern: {level: "snapshot"} with no atClusterTime,
mongos should retry a SnapshotError: it will choose a later timestamp for atClusterTime and may
succeed. If the client sends readConcern: {level: "snapshot", atClusterTime: T} and mongos get a
SnapshotError, there's no point retrying.
```

对应的 mongos 逻辑：

```cpp
// src/mongo/s/query/cluster_find.cpp:769-778
if (auto txnRouter = TransactionRouter::get(opCtx)) {
    if (!txnRouter.canContinueOnStaleShardOrDbError(kFindCmdName, ex.toStatus())) {
        throw;
    }
    txnRouter.onStaleShardOrDbError(opCtx, kFindCmdName, ex.toStatus());
    txnRouter.setDefaultAtClusterTime(opCtx);  // 重新选时间戳
}
```

`setDefaultAtClusterTime` 会用当前 VectorClock 的 clusterTime 重新设置：

```cpp
// src/mongo/s/transaction_router.cpp:1185-1209
void TransactionRouter::Router::setDefaultAtClusterTime(OperationContext* opCtx) {
    const auto defaultTime = VectorClock::get(opCtx)->getTime();
    if (o().atClusterTimeForSnapshotReadConcern) {
        if (o().atClusterTimeForSnapshotReadConcern->canChange(p().latestStmtId)) {
            setAtClusterTime(..., defaultTime.clusterTime());
        }
    }
}
```

#### B. 客户端显式提供 atClusterTime

**不重试**。因为客户端指定的固定时间戳如果不可用，重试也无效。直接返回 `SnapshotError` 给客户端。

`ReadConcernArgs` 区分了两种来源：

```cpp
// src/mongo/db/repl/read_concern_args.h:239-256
void setArgsAtClusterTimeForSnapshot(Timestamp ts) {
    // Only overwrite a server-selected atClusterTime, not user-supplied.
    invariant(_atClusterTime.is_initialized() == _atClusterTimeSelected);
    _atClusterTime = LogicalTime(ts);
    _atClusterTimeSelected = true;
}
bool wasAtClusterTimeSelected() const { return _atClusterTimeSelected; }
```

## 9. getMore 的特殊性与业务处理

### 9.1 为什么 getMore 不可重试

`getMore` 是游标拉取下一批数据的命令。如果在网络传输过程中失败，客户端无法知道：
- 服务端是否已经把游标前进了一格？
- 还是服务端根本没收到请求？

因此驱动**不会**自动重试 `getMore`。测试代码明确说明了这一点：

```js
// jstests/noPassthrough/auto_retry_on_network_error.js:88-100
// getMore commands can't be retried because we won't know whether the cursor was advanced or not.
let cursorId = assert.commandWorked(db.runCommand({find: collName, batchSize: 0})).cursor.id;
failNextCommand(db, "getMore");
assert.throws(function() {
    db.runCommand({getMore: cursorId, collection: collName});
});
```

### 9.2 业务侧如何处理 getMore 失败

```go
cursor, err := coll.Find(context.TODO(), bson.D{{"active", true}})
if err != nil {
    // find 失败已被自动重试，这里收到的是最终错误
    return err
}
defer cursor.Close(context.TODO())

for cursor.Next(context.TODO()) {
    // getMore 失败在这里暴露，驱动不会自动重试
    var doc bson.M
    if err := cursor.Decode(&doc); err != nil {
        return err
    }
    process(doc)
}
if err := cursor.Err(); err != nil {
    // getMore 期间的网络错误，需要业务自行处理
    // 选项 A：重新发起整个查询（需业务幂等）
    // 选项 B：记录进度后放弃
}
```

**这是 retryable reads 最主要的业务侧坑点**：对大结果集要特别小心 `getMore` 失败的处理。

## 10. 最佳实践与业务建议

### 10.1 何时使用 retryReads

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| 常规读操作 | `retryReads=true`（默认） | 驱动自动重试，应用无感知 |
| snapshot 读（无固定 atClusterTime） | `retryReads=true` | mongos 可重新选时间戳重试 |
| snapshot 读（固定 atClusterTime） | 需自行处理 `SnapshotError` | mongos 不会重试 |
| 大结果集游标 | 注意 getMore 失败处理 | getMore 不可重试 |
| 对延迟敏感的场景 | 可关闭 retryReads | 重试会增加尾延迟 |
| 分片部分故障 | 使用 `allowPartialResults` | 拿到部分结果而非整体失败 |

### 10.2 大结果集游标的最佳实践

```go
// 使用较大的 batchSize 减少 getMore 次数
opts := options.Find().SetBatchSize(1000)
cursor, err := coll.Find(context.TODO(), filter, opts)

// 或使用 CSOT 模式让 find 本身有更多重试机会
clientOpts := options.Client().
    ApplyURI("mongodb://localhost:27017").
    SetTimeout(30 * time.Second)
```

### 10.3 分片部分故障的处理

```js
const res = db.runCommand({
    find: "users",
    filter: {active: true},
    allowPartialResults: true
});
if (res.cursor.partialResultsReturned) {
    // 警告：结果不完整，部分分片不可用
}
```

### 10.4 关闭 retryReads 的场景

- **严格的延迟要求**：重试会增加尾延迟。如果业务宁可快速失败也不想等待重试。
- **自定义重试逻辑**：应用层有更精细的重试控制（如带指数退避）。
- **调试**：想看到真实的瞬时错误而不是被驱动吞掉。

## 12. 总结

Retryable reads 是一个**纯驱动层**、**对应用透明**、**默认开启**的读操作韧性机制。其设计要点：

### 驱动端核心（mongo-go-driver）

1. **读天然幂等**：不需要事务号去重（与 retryable writes 的关键区别），重试逻辑完全在驱动端完成。
2. **判定三要素**：首轮一次性判定 `retrySupported` + 用户开关 `retryEnabled` + 错误分类 `RetryableRead()`。
3. **错误分类**：依赖 `NetworkError` 标签 + `retryableCodes` 错误码列表，**不依赖服务端附加的标签**（与写重试不同）。
4. **智能重定向**：重试时通过 `Deprioritized` 选择器避开失败服务器，提高成功率。
5. **连接池友好**：`poolClearedError` 等连接池错误也会触发重试。
6. **CSOT 友好**：设置 `Timeout` 后自动转为按截止时间无限重试。
7. **过载自适应**：`SystemOverloadedError` 配合 `MaxAdaptiveRetries` 走独立的指数退避重试通道。
8. **边界明确**：事务内读、`RunCommand`、`$out`/`$merge` 写型 aggregate、`getMore` 均不重试。

### 服务端核心（MongoDB 8.0）

1. **不解析 retryReads**：服务端 `mongo_uri.cpp` 只识别 `retryWrites`，无 `RetryableReadError` 标签。
2. **通用重试基础设施**：`RetriableError` 错误码分类是驱动判定的依据。
3. **mongos 内部多层重试**：ARS（每 host 最多 3 次）+ ShardRemote（无限次直到取消），对客户端透明。
4. **snapshot 读 atClusterTime 重选**：mongos 可为未指定 atClusterTime 的 snapshot 读重新选择时间戳并重试。
5. **partialResultsReturned 容错**：分片部分故障时可返回部分结果。
6. **getMore 不可重试**：这是设计约束，不是缺陷——业务侧需自行处理大结果集游标的 getMore 失败。
