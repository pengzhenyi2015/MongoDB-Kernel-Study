## 1. 概述

### 1.1 什么是 Retryable Writes

Retryable Writes（可重试写）是 MongoDB 3.6+ 引入、在 4.2 中完善的写操作韧性机制。当一次写操作因**瞬时网络错误**或**主节点切换**等原因失败时，驱动会自动选择新服务器并使用**相同的事务号（txnNumber）**重试，利用服务端的幂等性保证不会产生重复写入。

**核心特征**：

| 维度 | 说明 |
|------|------|
| **默认状态** | 驱动端默认开启（`retryWrites=true`） |
| **重试上限** | 普通场景下只重试 **1 次**；CSOT 模式（设置了 Client 级 Timeout）下可在上下文截止前无限重试 |
| **幂等保证** | 通过 `lsid`（逻辑会话 ID）+ `txnNumber`（事务号）实现，服务端通过 oplog 去重 |
| **部署要求** | 必须运行在副本集或分片集群上（Standalone 不支持） |
| **前提条件** | 需要显式或隐式 Session、acknowledged WriteConcern |

### 1.2 双端协作模型

Retryable writes 是**驱动端与服务端协作**的机制，两端各司其职：

```
┌─────────────────────────────────────────────────────────────────────┐
│                         驱动端 (Driver)                              │
│                                                                     │
│  1. 解析 retryWrites=true 配置                                      │
│  2. 为写操作分配 RetryMode (RetryOnce / RetryOncePerCommand)        │
│  3. 发送命令前递增 txnNumber                                         │
│  4. 收到错误后判定是否可重试（依赖错误标签 / 错误码）                  │
│  5. 重试时复用相同 txnNumber，选择新服务器                            │
│  6. 处理 NoWritesPerformed 语义歧义                                  │
└────────────────────────────┬────────────────────────────────────────┘
                             │  命令附带 lsid + txnNumber
                             ▼
┌─────────────────────────────────────────────────────────────────────┐
│                       服务端 (Server)                                │
│                                                                     │
│  1. 解析命令中的 lsid + txnNumber                                    │
│  2. TransactionParticipant 维护事务号状态机                          │
│     - 新 txnNumber → 执行写入                                        │
│     - 相同 txnNumber → 返回缓存结果（幂等）                           │
│  3. 发生可重试错误时附加 RetryableWriteError 标签                     │
│  4. 附加 NoWritesPerformed 标签（确定未写入时）                       │
│  5. shard key 更新场景：升级为内部事务                                │
└─────────────────────────────────────────────────────────────────────┘
```

## 2. 使用场景

### 2.1 适用场景

| 场景 | 典型错误 | 重试效果 |
|------|---------|---------|
| **副本集故障转移** | `NotWritablePrimary`(10107)、`PrimarySteppedDown`(189)、`InterruptedDueToReplStateChange`(11602) | 等待新主就绪后在新主上成功，txnNumber 保证幂等 |
| **瞬时网络故障** | `HostUnreachable`(6)、`HostNotFound`(7)、`NetworkTimeout`(89)、`SocketException`(9001) | 自动重连并重试 |
| **服务端关闭中** | `ShutdownInProgress`(91)、`InterruptedAtShutdown`(11600) | 切换到健康节点重试 |
| **mongos 抖动** | mongos 到 shard 连接异常 | 驱动重选 mongos 或 mongos 内部重试 |
| **事务提交/中止** | commit/abort 期间的瞬时错误 | 自动重试，commit 升级为 majority WC |
| **服务端过载** | `SystemOverloadedError` | 配合 `MaxAdaptiveRetries` 带退避重试 |

### 2.2 不适用 / 不生效的场景

| 场景 | 原因 |
|------|------|
| `UpdateMany` / `DeleteMany` | 多文档操作无法用 txnNumber 保证幂等 |
| Standalone 部署 | `retryWritesSupported` 返回 false，服务端不支持事务号 |
| unacknowledged WriteConcern（`{w: 0}`） | 驱动无法确认写入结果，无法安全重试 |
| 无 Session 的操作 | 写重试要求 `op.Client != nil`（必须有 Session） |
| 事务内的 CRUD 操作 | 仅 commit/abort 可重试，CRUD 由事务语义保证 |
| 含 `UpdateManyModel`/`DeleteManyModel` 的 BulkWrite | 多文档操作破坏幂等保证 |
| `RunCommand`（裸命令） | 不参与驱动重试机制 |

## 5. 驱动端实现原理（mongo-go-driver）

### 5.1 核心类型：RetryMode 与 Type

`x/mongo/driver/driver.go` 定义了驱动内部描述操作类型与重试策略的基础类型：

```go
type Type uint

const (
    _ Type = iota
    Write
    Read
)

type RetryMode uint

const (
    RetryNone RetryMode = iota          // 不重试
    RetryOnce                           // 整个操作重试一次
    RetryOncePerCommand                 // 每个分批命令各重试一次
    RetryContext                        // 重试直到 context 截止
)

func (rm RetryMode) Enabled() bool {
    return rm == RetryOnce || rm == RetryOncePerCommand || rm == RetryContext
}
```

- 写操作被标记为 `Type: Write`。
- `RetryOncePerCommand`：适用于可分批的写（insert/update/delete），每个批次各享有 1 次重试。
- `RetryOnce`：适用于单命令写（findAndModify）。

### 5.2 各写操作的 Wiring

驱动在 `mongo/collection.go` 中为每种写操作设置 RetryMode：

**InsertOne / InsertMany**：
```go
retry := driver.RetryNone
if coll.client.retryWrites {
    retry = driver.RetryOncePerCommand
}
```

**DeleteOne（DeleteMany 不可重试）**：
```go
// deleteMany cannot be retried
retryMode := driver.RetryNone
if deleteOne && coll.client.retryWrites {
    retryMode = driver.RetryOncePerCommand
}
```

**UpdateOne / ReplaceOne（UpdateMany 不可重试）**：
```go
retry := driver.RetryNone
// retryable writes are only enabled updateOne/replaceOne operations
if !multi && coll.client.retryWrites {
    retry = driver.RetryOncePerCommand
}
```

**FindOneAndDelete / Replace / Update**：
```go
retry := driver.RetryNone
if coll.client.retryWrites {
    retry = driver.RetryOnce
}
```

**BulkWrite**：只有当批次内**所有 model 都是单文档操作**时才可重试：
```go
if bw.collection.client.retryWrites && batch.canRetry {
    retry = driver.RetryOncePerCommand
}
```

### 5.3 核心状态机：Operation.Execute

`x/mongo/driver/operation.go` 的 `func (op Operation) Execute(ctx context.Context) error` 是重试逻辑的中枢。

#### 5.3.1 计算重试预算

```go
case Write:
    if op.Client == nil {       // 写重试必须有 Session
        break
    }
    switch *op.RetryMode {
    case RetryOnce, RetryOncePerCommand:
        defaultRetries = ptrutil.Ptr(uint(1))   // 1 次
    case RetryContext:
        defaultRetries = nil                     // 无限
    }
// CSOT 模式：只要启用了重试就改为无限
if csot.IsTimeoutContext(ctx) && op.RetryMode.Enabled() {
    defaultRetries = nil
}
```

#### 5.3.2 首轮判定 retryable

`retryable()` 只在第一次连接上判定一次，此后不再重新评估：

```go
func (op Operation) retryable(desc description.Server) bool {
    switch op.Type {
    case Write:
        // 事务提交/中止：无条件可重试
        if op.Client != nil && (op.Client.Committing || op.Client.Aborting) {
            return true
        }
        // 普通写：需满足服务端支持 + 非 Standalone + 有 Session + 不在事务中 + acknowledged WC
        if retryWritesSupported(desc) &&
            op.Client != nil && (!op.Client.TransactionInProgress() && !op.Client.TransactionStarting()) &&
            op.WriteConcern.Acknowledged() {
            return true
        }
    }
    return false
}
```

`retryWritesSupported`：
```go
func retryWritesSupported(s description.Server) bool {
    return s.SessionTimeoutMinutes != nil && s.Kind != description.ServerKindStandalone
}
```

#### 5.3.3 事务号递增（幂等的关键）

首轮若支持重试，会预先递增 txnNumber。重试时**复用同一个 txnNumber**，服务端据此识别"这是同一次操作的重新提交"，通过 oplog 去重。

#### 5.3.4 错误分类与重试决策

```go
retryableErr := tt.Retryable(connDesc.Kind, connDesc.WireVersion)
preRetryWriteLabelVersion := connDesc.WireVersion != nil && connDesc.WireVersion.Max < 9
inTransaction := op.Client != nil &&
    (!op.Client.Committing && !op.Client.Aborting) && op.Client.TransactionRunning()
// pre-4.4 服务端：客户端手动补打 RetryableWriteError 标签
if retryableErr && preRetryWriteLabelVersion && retryEnabled && !inTransaction {
    tt.Labels = append(tt.Labels, RetryableWriteError)
}
needRetry := (retrySupported && retryEnabled && retryableErr)

if needRetry && (allowedRetries == nil || attempt < *allowedRetries) {
    if op.Client != nil && op.Client.Committing {
        // 提交事务的重试：升级为 majority write concern
        op.Client.UpdateCommitTransactionWriteConcern()
        op.WriteConcern = op.Client.CurrentWc
    }
    if err = resetForRetry(tt); err != nil { return err }
    continue
}
```

#### 5.3.5 resetForRetry：重试前的状态复位

```go
resetForRetry := func(err error) error {
    attempt++
    prevErr = err
    // NoWritesPerformed / driver-exception / CSOT 的 prevIndefiniteErr 管理
    ...
    if conn != nil {
        // 分片拓扑或开了 overload retargeting：把失败服务器加入降权列表
        if op.Deployment.Kind() == description.TopologyKindSharded ||
            (isOverloadedError && op.EnableOverloadRetargeting) {
            deprioritizedServers = append(deprioritizedServers, conn.Description())
        }
        conn.Close()
    }
    srvr = nil   // 强制下一轮重新选服务器
    conn = nil   // 强制下一轮重新获取连接
    return nil
}
```

#### 5.3.6 分批推进时重置重试预算

`RetryOncePerCommand` 模式下，当一个批次成功推进到下一批次时，重试计数器会重置——即每个批次都独立享有一次重试机会。

### 5.4 错误分类：哪些写错误会重试

`x/mongo/driver/errors.go` 提供三个层级的分类函数，均**wire-version aware**：

**可重试错误码列表**：

```go
retryableCodes = []int32{
    6,     // HostUnreachable
    7,     // HostNotFound
    89,    // NetworkTimeout
    91,    // ShutdownInProgress
    134,   // ReadConcernMajorityNotAvailableYet
    189,   // PrimarySteppedDown
    262,   // ExceededTimeLimit
    9001,  // SocketException
    10107, // NotWritablePrimary
    11600, // InterruptedAtShutdown
    11602, // InterruptedDueToReplStateChange
    13435, // NotPrimaryNoSecondaryOk
    13436, // NotPrimaryOrSecondary
}
```

**Wire Version 分层逻辑**：

| 服务端版本 | WireVersion.Max | 重试判定依据 |
|-----------|----------------|-------------|
| 4.4+ | >= 9 | 完全信任服务端返回的 `RetryableWriteError` 标签 |
| pre-4.4 | < 9 | 客户端依据 `retryableCodes` 自行判定，并补打标签 |
| pre-4.4 mongos | < 9 + Mongos | `WriteConcernError` 不重试（mongos 已自重试） |

`WriteCommandError.Retryable`：
```go
func (wce WriteCommandError) Retryable(serverKind description.ServerKind, wireVersion *description.VersionRange) bool {
    for _, label := range wce.Labels {
        if label == RetryableWriteError { return true }   // 信任服务端标签
    }
    if wireVersion != nil && wireVersion.Max >= 9 {       // 4.4+：完全依赖标签
        return false
    }
    if wce.WriteConcernError == nil { return false }
    return wce.WriteConcernError.Retryable(serverKind, wireVersion)
}
```

### 5.5 NoWritesPerformed 标签：幂等安全的关键

`NoWritesPerformed` 表示服务端**确定没有执行任何写入**。驱动用它来处理"上一次尝试可能已写入，但这次确定没写"的语义歧义。

**在 `resetForRetry` 中**：记录 `prevIndefiniteErr`（"不确定是否写入"的错误）时，若当前错误带 `NoWritesPerformed`，则**不更新** `prevIndefiniteErr`——因为明确没写入的错误比之前的"不确定"错误更确定，应保留之前的"不确定"错误作为最终返回。

```go
if lerr, ok := err.(labeledError); ok {
    if !lerr.HasErrorLabel(NoWritesPerformed) {
        var serverErr Error
        isDriverException := errors.As(err, &serverErr) && serverErr.Code != 0
        isCSOTTimeout := errors.Is(err, context.DeadlineExceeded) || errors.Is(err, context.Canceled)
        if isDriverException && !isCSOTTimeout {
            prevIndefiniteErr = err
        }
    }
}
```

**重试最终失败时**：
```go
if tt.HasErrorLabel(NoWritesPerformed) && !prevIndefiniteErrIsSet {
    err = prevIndefiniteErr           // 返回之前"可能已写入"的错误
    prevIndefiniteErrIsSet = true
    goto checkError
}
```

**意义**：若首次尝试可能已写入（如网络超时），重试后服务端报告"未执行写入"，驱动会返回首次的"不确定"错误而非误导性的"未写入"，让应用层知道**数据可能已经写入**，需要谨慎处理。

### 5.6 事务与 Retry Writes 的交互

| 场景 | 是否重试 | 说明 |
|------|---------|------|
| 事务内 CRUD | ❌ | `retryable()` 对 `TransactionInProgress`/`TransactionStarting` 返回 false |
| 事务 Commit | ✅ | `Committing` 状态下无条件可重试，且重试时 WC 升级为 majority |
| 事务 Abort | ✅ | `Aborting` 状态下无条件可重试 |

事务的 commit/abort 在 `mongo/session.go` 中通过 `Retry(driver.RetryOncePerCommand)` 启用重试。提交重试时会调用 `UpdateCommitTransactionWriteConcern()` 将 write concern 升级为 majority，确保提交结果的确定性。

commit 的 writeConcern 错误会被打上 `UnknownTransactionCommitResult` 标签，表示"提交结果未知"，应用需自行决定是否再次重试。

### 6.2 服务端如何识别 retryable write

### 6.3 RetryableWriteError 标签

服务端在发生可重试错误时给响应打上 `RetryableWriteError` 标签，由驱动决定重试。判断逻辑在 src/mongo/db/error_labels.cpp:80-120：

```cpp
bool ErrorLabelBuilder::isRetryableWriteError() const {

        return false;
    }

        return _sessionOptions.getTxnNumber() && !_sessionOptions.getAutocommit();
    };

    if (isRetryableWrite() || isTransactionCommitOrAbort()) {

        return !_isMongos &&
            ((_code && ErrorCodes::isRetriableError(_code.value())) ||
             (_wcCode && ErrorCodes::isRetriableError(_wcCode.value())));
    }
    return false;
}
```

### 6.4 服务端事务号状态机

每个会话通过 `TransactionParticipant` 维护当前 `activeTxnNumberAndRetryCounter`。

核心入口 `beginOrContinue()`（src/mongo/db/transaction/transaction_participant.cpp:1046-1113）：

```cpp
void TransactionParticipant::Participant::beginOrContinue(
    OperationContext* opCtx,
    TxnNumberAndRetryCounter txnNumberAndRetryCounter,
    boost::optional<bool> autocommit,
    TransactionActions action) {
    ...
    // 请求没有 autocommit 则为 retryable write
    if (!autocommit) {
        invariant(action == TransactionActions::kNone);
        _beginOrContinueRetryableWrite(opCtx, txnNumberAndRetryCounter);
        return;
    }
    ...
}
```

`_beginOrContinueRetryableWrite` 实现了核心的"新写/重试"判定（transaction_participant.cpp:890-923）：

```cpp
void TransactionParticipant::Participant::_beginOrContinueRetryableWrite(
    OperationContext* opCtx, const TxnNumberAndRetryCounter& txnNumberAndRetryCounter) {
    ...
    if (txnNumberAndRetryCounter.getTxnNumber() >
        o().activeTxnNumberAndRetryCounter.getTxnNumber()) {
        // New retryable write.
        _setNewTxnNumberAndRetryCounter(...);
        p().autoCommit = boost::none;
        // 注册到 RetryableWriteTransactionParticipantCatalog
    } else {
        // Retrying a retryable write.
        uassert(ErrorCodes::PreparedTransactionInProgress,
                "Retryable write that has been converted to a transaction is in prepare",
                !o().txnState.isInSet(TransactionState::kPrepared));

        uassert(ErrorCodes::IncompleteTransactionHistory,
                "Cannot retry a retryable write that has been converted into a transaction",
                o().txnState.isInRetryableWriteMode());
    }
}
```

**状态机关键点**：

| 场景 | 服务端行为 |
|------|-----------|
| `txnNumber > activeTxnNumber` | **新写**：执行写入，记录结果 |
| `txnNumber == activeTxnNumber`（重试） | **幂等返回**：返回缓存的执行结果 |
| retryable write 已升级为事务 | 抛 `IncompleteTransactionHistory` |
| 事务在 prepare 阶段 | 抛 `PreparedTransactionInProgress` |

### 6.5 服务端内部重试执行器

对于 mongos 内部调用，通用的异步 RPC 重试循环在 src/mongo/executor/async_rpc.h:251-317：


## 8. shard key 更新场景深度分析

这是 retryable writes 最复杂的边界场景，涉及驱动与服务端的深度协作。

### 8.1 核心问题

当 `update` 修改了文档的 shard key，导致文档需要从一个分片迁移到另一个分片时，单个 `update` 命令无法原子完成"删除旧文档 + 插入新文档"两个操作。MongoDB 对此有一套专门的升级机制。

### 8.2 WouldChangeOwningShard 错误

分片执行 `update` 时，在 src/mongo/db/exec/update_stage.cpp:855-879 检测新的 shard key 是否仍属于当前分片：

```cpp
if (!collFilter->keyBelongsToMe(newShardKey)) {
    ...
    auto& collectionPtr = _collAcq.getCollectionPtr();
    uasserted(WouldChangeOwningShardInfo(oldObj.value(),
                                         newObj,
                                         false /* upsert */,
                                         collectionPtr->ns(),
                                         collectionPtr->uuid()),
              "This update would cause the doc to change owning shards");
}
```

错误信息包含 pre-image（旧文档）和 post-image（新文档），供 mongos 做后续处理。

### 8.3 mongos 分发逻辑

mongos 在 src/mongo/s/commands/cluster_write_cmd.cpp:307-405 捕获 `WouldChangeOwningShard`：

```cpp
bool ClusterWriteCmd::handleWouldChangeOwningShardError(...) {
    auto txnRouter = TransactionRouter::get(opCtx);
    bool isRetryableWrite = opCtx->getTxnNumber() && !txnRouter;
    ...
}
```

判定条件 `opCtx->getTxnNumber() && !txnRouter`：
- `txnNumber` 存在：这是一个可重试写。
- 没有 `TransactionRouter`：它不是一个显式多文档事务。

### 8.4 batch size 限制

如果 batch 大小超过 1，分片 key 更新导致文档跨分片移动是不允许的：

```cpp
if (request.sizeWriteOps() != 1U) {
    ...
    uasserted(ErrorCodes::InvalidOptions,
              "Document shard key value updates that cause the doc to move shards "
              "must be sent with write batch of size 1");
}
```

### 8.5 两条实现路径

#### A. 新 Transaction API 路径（默认启用时）

通过 `gFeatureFlagUpdateDocumentShardKeyUsingTransactionApi` 控制。如果当前是 retryable write，会调用 `handleWouldChangeOwningShardErrorNonTransaction`，启动一个内部事务：

```cpp
auto txn = txn_api::SyncTransactionWithRetries(
    opCtx, executor, nullptr, inlineExecutor);

BSONObjBuilder cmdWithStmtId(request->toBSON());
cmdWithStmtId.append(write_ops::WriteCommandRequestBase::kStmtIdFieldName, 0);

auto swCommitResult = txn.runNoThrow(
    opCtx, [sharedBlock](const txn_api::TransactionClient& txnClient, ExecutorPtr txnExec) {
        return txnClient.runCommand(sharedBlock->nss.dbName(), sharedBlock->cmdObj)
            .thenRunOn(txnExec)
            .then([sharedBlock](auto res) {
                uassertStatusOK(getStatusFromWriteCommandReply(res));
            })
            .semi();
    });
```

#### B. Legacy 路径

当 feature flag 关闭时走 legacy 路径，调用 `handleWouldChangeOwningShardErrorRetryableWriteLegacy`（document_shard_key_update_util.cpp:198-273）：

```cpp

updatedShardKey =
    wouldChangeOwningShardErrorInfo &&
    updateShardKeyForDocumentLegacy(
        opCtx, nss, *wouldChangeOwningShardErrorInfo, nss.isTimeseriesBucketsCollection());

```

### 8.6 delete + insert 原子移动文档

实际移动文档由 `executeOperationsAsPartOfShardKeyUpdate` 完成（document_shard_key_update_util.cpp:74-122）：

```cpp
bool executeOperationsAsPartOfShardKeyUpdate(OperationContext* opCtx,
                                             const BSONObj& deleteCmdObj,
                                             const BSONObj& insertCmdObj, ...) {
    // 1. 在源分片删除旧文档
    auto deleteRequest = BatchedCommandRequest::parseDelete(deleteOpMsg);
    cluster::write(opCtx, deleteRequest, nullptr, &deleteStats, &deleteResponse);

    // 2. 在目标分片插入新文档（通过路由表自动路由）
    auto insertRequest = BatchedCommandRequest::parseInsert(insertOpMsg);
    cluster::write(opCtx, insertRequest, nullptr, &insertStats, &insertResponse);
}
```

在新 Transaction API 版本中，通过 `kUninitializedStmtId` 显式选择不存储重试历史：

```cpp
return txnClient.runCRUDOp(deleteRequest, {kUninitializedStmtId})
    .thenRunOn(txnExec)
    .then([&](auto deleteResponse) -> SemiFuture<BatchedCommandResponse> {
        ...
        return txnClient.runCRUDOp(insertRequest, {kUninitializedStmtId});
    })
```

### 8.7 强制两阶段提交

为了保证重试语义，shard key 更新升级后的事务**强制走两阶段提交**：

```cpp
if (TransactionRouter::get(opCtx)) {
    TransactionRouter::get(opCtx).disallowSingleWriteShardCommit();
}
```

即使所有写操作落在一个分片上，也不会走优化后的单分片提交，确保重试时能被识别为已升级的事务。

### 8.8 为什么重试 shard key 更新会失败

这是**设计的预期行为**。原始 retryable write 被升级为一个内部事务后，会话状态从"retryable write mode"变为"transaction mode"。当驱动再次用相同的 `txnNumber` 重试时，`TransactionParticipant` 会抛出：

```cpp
uassert(ErrorCodes::IncompleteTransactionHistory,
        "Cannot retry a retryable write that has been converted into a transaction",
        o().txnState.isInRetryableWriteMode());
```

测试文件 jstests/sharding/move_chunk_update_shard_key_in_retryable_write.js:1-14 明确说明了这一点：

> When we update a shard key such that a document moves from one shard to another, and the update is sent as a retryable write, the update is converted into a multi-statement transaction with the same transaction number. The new transaction contains a delete on the source shard and an insert on the destination shard. If original update is retried, it should receive an error saying that the write can't be retried since it was upgraded to a transaction as part of the update.

## 9. 最佳实践与业务建议

### 9.1 何时使用 retryWrites

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| 单文档写入、小 batch | `retryWrites=true`（默认） | 驱动自动重试，应用无感知 |
| 修改 shard key 的 update | **显式事务** | retryable write 升级后不可重试，会返回 `IncompleteTransactionHistory` |
| 多文档原子操作 | **显式事务** | retryable write 不保证多文档原子性 |
| 对延迟敏感的场景 | 可关闭 retryWrites | 重试会增加尾延迟 |
| 需要精细控制重试 | 可关闭并自定义 | 应用层实现退避策略 |

### 9.2 shard key 更新的正确处理方式

**不要用 retryable write 执行会修改 shard key 的 update**。应使用显式事务：

```go
session, err := client.StartSession()
defer session.EndSession(context.TODO())

_, err = session.WithTransaction(context.TODO(), func(sessCtx mongo.SessionContext) error {
    _, e := coll.UpdateOne(
        sessCtx,
        bson.D{{"_id", 1}},
        bson.D{{"$set", bson.D{{"shardKey", "newValue"}}}},
    )
    return e
})
```

如果必须使用 retryable write，应用层应捕获 `IncompleteTransactionHistory` 错误，并通过查询确认文档最终状态。

### 9.3 BulkWrite 的注意事项

```go
// ✅ 全是单文档操作 → 可重试
models := []mongo.WriteModel{
    mongo.NewInsertOneModel().SetDocument(bson.D{{"v", 1}}),
    mongo.NewUpdateOneModel().Filter(bson.D{{"_id", 2}}).Update(bson.D{{"$set", bson.D{{"v", 2}}}}),
    mongo.NewDeleteOneModel().Filter(bson.D{{"_id", 3}}),
}
_, err := coll.BulkWrite(context.TODO(), models)

// ❌ 含 DeleteManyModel → 该批次不可重试
models2 := []mongo.WriteModel{
    mongo.NewInsertOneModel().SetDocument(bson.D{{"v", 1}}),
    mongo.NewDeleteManyModel().Filter(bson.D{{"status", "old"}}),
}
_, err = coll.BulkWrite(context.TODO(), models2)
```


## 11. 总结

Retryable writes 是一个**驱动端与服务端协作**、**对应用透明**、**默认开启**的写操作韧性机制。其设计要点：

### 驱动端核心（mongo-go-driver）

1. **幂等保证**：通过递增 txnNumber 并在重试时复用，借助服务端 oplog 实现去重，确保不会因重试产生重复写入。
2. **分层错误判定**：4.4+ 完全信任服务端 `RetryableWriteError` 标签；pre-4.4 由客户端依据 `retryableCodes` 自行判定并补打标签。
3. **操作类型限制**：仅单文档写（含 findAndModify）可重试；多文档写（UpdateMany/DeleteMany）因无法保证幂等而被排除。
4. **NoWritesPerformed 语义**：精心处理"可能已写入"与"确定未写入"的歧义，返回更安全的错误。
5. **CSOT 友好**：设置 `Timeout` 后自动转为按截止时间无限重试。
6. **事务友好**：事务内 CRUD 不重试，但 commit/abort 可重试，且 commit 重试升级为 majority WC。

### 服务端核心（MongoDB 8.0）

1. **事务号状态机**：`TransactionParticipant` 维护每个 session 的事务号状态，对相同 `txnNumber` 的请求直接返回已执行结果（幂等）。
2. **错误标签机制**：服务端通过 `ErrorLabelBuilder` 在可重试错误上附加 `RetryableWriteError` 标签，驱动据此决定重试。
3. **shard key 更新升级**：当 retryable write 触发 shard key 跨分片更新时，mongos 将其**升级为内部事务**（delete + insert），强制两阶段提交。升级后的 write 不再能被重试，返回 `IncompleteTransactionHistory`。
4. **业务建议**：避免用 retryable write 执行会修改 shard key 的 update，应使用显式事务。
