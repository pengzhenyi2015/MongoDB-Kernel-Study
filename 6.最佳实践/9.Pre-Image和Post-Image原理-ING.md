# 1. 导语

Pre-image 是文档被替换 / 更新 / 删除之前的完整快照，post-image 是文档被插入 / 替换 / 更新之后的完整快照。     

MongoDB 6.0 起，change stream 通过集合级选项 changeStreamPreAndPostImages 支持在事件中携带这两类快照； 7.0 $changeStreamSplitLargeEvent 支持拆分超过 16MB 的事件（对同时携带前后镜像的大文档事件至关重要）；8.0 沿用了 6.0
引入的机制，并在性能与批量写入 oplog 行为上做了改进。

# 2. 用法
## 2.1 为集合开启 pre/post-image 记录（集合级）
```
// 方式一：修改已有集合
db.runCommand({
 collMod: "orders",
 changeStreamPreAndPostImages: { enabled: true }
})
// 方式二：创建集合时指定
db.createCollection("orders", { changeStreamPreAndPostImages: { enabled: true } })
// 验证
db.getCollectionInfos({ name: "orders" })[0].options.changeStreamPreAndPostImages
// => { enabled: true }
```

## 2.2 配置镜像保留策略（集群级，可选）
```
// 显式 TTL：100 秒（整个集群生效）
db.adminCommand({
 setClusterParameter: {
 changeStreamOptions: { preAndPostImages: { expireAfterSeconds: 100 } }
 }
})
// "off" = 跟随 oplog 保留窗口（默认策略）
db.adminCommand({
 setClusterParameter: {
 changeStreamOptions: { preAndPostImages: { expireAfterSeconds: "off" } }
 }
})
// 查看当前配置
db.adminCommand({ getClusterParameter: "changeStreamOptions" })
```

**即使设了 expireAfterSeconds ，只要对应 change stream 事件已被挤出oplog，其 pre/post-image 也会被删除；反过来， expireAfterSeconds: "off" 表示镜像与oplog 事件同生共死。**

## 2.3 打开 change stream 时声明所需镜像
ChangeStream 增加了 2 个参数：
- fullDocumentBeforeChange, 即 pre-image. 对应 update/delete 操作。
- fullDocument，即 post-image. 对应 update/insert 操作。

|选项|取值|行为|
|:--|:--|:--|
|fullDocumentBeforeChange|off （默认）|不返回 pre-image|
||whenAvailable|有则返回，无则该字段为 null|
||required|无 pre-image 时报错（NoMatchingDocument ）|
|fullDocument|default （默认）|update 事件只有 delta|
||updateLookup|事件处理时回查业务集合，返回"更新之后某时刻"的多数派版本（非时间点精确，文档已删则为 null）|
||whenAvailable|返回写入时物化/可合成的时间点精确post-image，不可得为 null|
||required|同上，不可得时报错|

**注意** updateLookup 与 whenAvailable / required是互斥的不同取值，不能组合；并且未开启 changeStreamPreAndPostImages 的集合上设whenAvailable 只能拿到 insert/replace 事件的 post-image（它们本来就存在 oplog 的 o字段里），update 事件的 post-image 拿不到。

# 3. Pre-image 和 Post-image 原理

## 3.1 Pre-image 捕获和存储
Pre-Image 在写请求执行器中被捕获，然后存储在 config.system.preimages 表中。

写入路径涉及三个层次，全部位于同一个存储事务内：    
1. **执行层捕获旧文档**。 UpdateStage / DeleteStage 在执行更新或删除前读出旧文档，挂到 CollectionUpdateArgs::preImageDoc （delete 则是 aboutToDelete 传入的待删文档）。    
2. **OpObserver 标记记录方式**。 OpObserverImpl::onUpdate 检查 args.updateArgs->changeStreamPreAndPostImagesEnabledForCollection，若开启则执行：
```
invariant(!args.updateArgs->preImageDoc.isEmpty(), "Pre-image document must be present for pre-image recording");
operation.setPreImage(args.updateArgs->preImageDoc.getOwned());
operation.setChangeStreamPreImageRecordingMode(ChangeStreamPreImageRecordingMode::kPreImagesCollection);
```
3. **同一事务落盘**。 ChangeStreamPreImagesCollectionManager::insertPreImage 开头就有断言 tassert(6646200, "Expected to be executed in a write unit of work", ...)，证明 pre-image 插入与业务写、oplog 写在同一个 WriteUnitOfWork 中原子提交（change_stream_pre_images_collection_manager.cpp r8.0.0）。这意味着：业务写成功则镜像必然存在，不存在"文档改了但镜像丢了"的中间态（rollback 场景除外——rollback 会同时回滚镜像写入）。

两个容易混淆的旁路机制：    
- **多文档事务**：事务内的写先把操作暂存在 TransactionParticipant 里，pre-image 随操作对象携带，commit 时经 applyOps oplog 条目统一落盘；镜像与事务的原子性天然一致。    
- **可重试的 findAndModify**：这是另一套独立机制——oplog 条目上打 needsRetryImage 标记，镜像写入 config.image_collection （供 preImageOpTime / postImageOpTime 链接的 noop oplog 条目引用），与 change stream 的 config.system.preimages 互不相关。    

**复制行为**： config.system.preimages 的写入本身不作为数据复制；secondary 在回放 oplog 时重新执行写操作并本地生成 pre-image 写入自己的 preimages 集合。其好处是网络流量不放大，代价是 secondary 也要承担镜像写入的 I/O。    

### 存储结构：config.system.preimages    
pre-image 文档的 BSON 结构（由源码中的 ChangeStreamPreImage / ChangeStreamPreImageId 类型字段名确认）：
```
{
_id: { // ChangeStreamPreImageId
 nsUUID: UUID("..."), // 源集合 UUID（注意不是名字，rename 后仍能对应）
 ts: Timestamp(...), // 产生该镜像的写操作的 oplog 时间戳
 applyOpsIndex: 0 // 在 applyOps（事务）条目内的序号，非事务恒为 0
 },
 preImage: { ... }, // 变更前的完整文档
 operationTime: ISODate(...) // 墙钟时间，用于 TTL 判定
}
```
该集合是按 _id 的 clustered collection（ createPreImagesCollection 中设置 clusteredIndex ），即文档物理上按 {nsUUID, ts, applyOpsIndex} 排序存储。这一设计一箭双雕：读取端按 _id 做点查是常数路径；清理端按 nsUUID 前缀 + ts 范围做区间删除或 truncate，无需扫描无关集合的镜像（getAbsoluteMinPreImageRecordIdBoundForNs / toRecordId 正是把 ChangeStreamPreImageId 编码成 clustered RecordId）。
