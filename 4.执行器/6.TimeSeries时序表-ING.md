# 1. 导语

Mongo 5.0 内核开始，支持了时序数据库，并在随后的版本中，继续优化了时序数据库的性能和功能。

本文结合 8.0 内核版本代码，阐述如下几个问题：

- 基本用法：由于官方文档的描述足够详细，因此这里只是简要介绍，作为快速上手的笔记；
- 存储方式：这是整篇文章以及 MongoDB 时序表的核心，MongoDB 时序数据库的存储方式是基于行组（row-group）压缩的列存表，以及可读写的视图；
- 牺牲的功能：事务和 ChangeStream 等。时序表相对时序数据确实有很大的性能提升，但是也带来了不少的限制，损失了普通表的很多功能；
- 横向对比 TimescaleDB：同样是 row-group 压缩，但具体实现上和 MongoDB 的时序表却有很多不同，通过对比优缺点，加深我们的理解；
- 性能评估：使用通用的 TimeSeries Benchmark Suite 压测工具，评估 MongoDB 时序表的性能，包括导数据、查询性能、压缩率等指标。

# 2. 基本用法

## 2.1 创建时序表

时序表支持非分片表，也支持分片表。

以在副本集中创建非分片表为例，一个典型的建表语句为：

```javascript
db.createCollection("cpu", {
  timeseries: {
    timeField: "timestamp",
    metaField: "tags",
    granularity: "seconds"
  }
})
```

时序表逻辑上会按照时空分割成多个 bucket（有些数据库也称作 chunk），而上述建表语句则指定了时空划分的规则：

1. 空间划分

   **`metaField` 指定了空间划分的字段**，不同的 metaField 会被路由到不同的 bucket 上进行读写。

   以机器的监控数据为例，metaField 可以是机器 ID。

   metaField 的取值可以多一点，这样会增加 bucket 的数量，提升并发度，在数据查询时，也能进行快速过滤。

   但是 metaField 也**不要是高基维数据**。因为这样会打开特别多的 bucket，系统开销增大，而且每个 bucket 可能只会有少量的数据，这样发挥不出列存压缩存储的优势。

2. 时间划分

   **`timeField` 和 `granularity` 指定了时间划分的字段和时间粒度**。

   其中要特别说明的是 `granularity` 是一个时间单位，它决定了一个 bucket 的时间跨度。

   指定了 `granularity` 之后，内核中会给时序表确定 2 个时间窗口阈值：

   1. `bucketRoundingSeconds`：决定新测量归入哪个 bucket（参考 `getBucketRoundingSecondsFromGranularity`）。`roundTimestampToGranularity` 调用 `roundTimestampBySeconds` 向下取整，作为 bucket 的打开时间。
   2. `bucketMaxSpanSeconds`：决定一个 bucket 中数据的最大时间跨度（参考 `getMaxSpanSecondsFromGranularity`），消费点：
      - 写入路径：`control.max.timestamp - control.min.timestamp` 超过它就不再往该桶合入（关桶条件之一）；
      - TTL：删除条件为 `safeExpirationDate = now - expireAfterSeconds - bucketMaxSpanSeconds`，这也是为什么 `granularity` 越大，实际过期会**多等**一段时间；
      - 查询路径：`generateViewPipeline` 把它传给 `$_internalUnpackBucket` 做桶级裁剪。

三者之间的对应关系为：

| granularity | bucketMaxSpanSeconds | bucketRoundingSeconds |
| :-- | :-- | :-- |
| seconds（默认） | 3600（1h） | 60（1min） |
| minutes | 86400（1d） | 3600（1h） |
| hours | 2592000（30d） | 86400（1d） |
| 自定义 | 1 - 31536000 | 必须等于 maxSpan |

1 个自定义固定分桶的例子为：

```javascript
db.createCollection("hourly", {
  timeseries: {
    timeField: "timestamp",
    metaField: "sensorId",
    bucketMaxSpanSeconds: 3600,
    bucketRoundingSeconds: 3600
  }
})   // 两者必须相等
```

上述建表实际做了 3 件事：

1. **创建 system.buckets.cpu**：聚簇集合（clustered on _id），带 `$jsonSchema` 校验器（required _id/control/data，control.version 版本信息等，参考[附录 A](#附录-asystembuckets-集合的-jsonschema)）。

   正常情况下，用户都是通过视图进行读写，不会直接操作底层的 `system.buckets.*` 表。

2. **创建默认复合索引**。可以通过视图和 `system.buckets` 表查询索引情况：

   ```javascript
   mymongo80:PRIMARY> db.system.buckets.cpu.getIndexes()
   [
           {
                   "v" : 2,
                   "key" : {
                           "meta" : 1,
                           "control.min.timestamp" : 1,
                           "control.max.timestamp" : 1
                   },
                   "name" : "tags_1_timestamp_1"
           }
   ]

   // 视图中的索引，其实和 system.buckets 表中的索引一致，只是 tags 统一成了 meta，
   // timestamp 变成了 control.min.timestamp 和 control.max.timestamp
   mymongo80:PRIMARY> db.cpu.getIndexes()
   [
           {
                   "v" : 2,
                   "key" : {
                           "tags" : 1,
                           "timestamp" : 1
                   },
                   "name" : "tags_1_timestamp_1"
           }
   ]
   ```

3. **在 system.views 中插入视图定义**：

   ```json
   {
           "_id" : "benchmark_ts.cpu",
           "viewOn" : "system.buckets.cpu",
           "pipeline" : [
                   {
                           "$_internalUnpackBucket" : {
                                   "timeField" : "timestamp",
                                   "metaField" : "tags",
                                   "bucketMaxSpanSeconds" : 3600
                           }
                   }
           ]
   }
   ```

## 2.2 其他常用的建表选项

还有一些额外的参数，可以指定时序表的属性，常见的包括指定块级压缩算法和数据过期淘汰规则。

**块压缩算法**

如果不特别指定，内核会默认对时序表使用 zstd 压缩算法（普通表是 snappy）。

可以通过 `storageEngine` 参数强制指定块级压缩，比如下面的建表语句关闭块级压缩：

```javascript
// 如果通过 block_compressor 指定了压缩算法，则以用户指定的为准
db.createCollection("cpu_block_nocompressor", {
  timeseries: {
    timeField: "timestamp",
    metaField: "tags",
    granularity: "seconds"
  },
  storageEngine: {
    wiredTiger: { configString: "block_compressor=none" }
  }
})
```

> 块级压缩和列存压缩是分开的，即使关闭了块级压缩，列存压缩也会生效。

**过期时间**

可以通过 `expireAfterSeconds` 参数指定数据过期时间，到期后的数据会被自动删除。比如下面的建表语句：

```javascript
db.createCollection("weather", {
  timeseries: {
    timeField: "timestamp",
    metaField: "sensorId",
    granularity: "seconds"
  },
  expireAfterSeconds: 21600
})
```

和普通表通过 TTL 索引删除数据不同，`expireAfterSeconds` 参数并不会创建 TTL 索引，所以通过 `getIndexes` 看不到 TTL 索引信息。但是可以通过 `getCollectionInfos` 命令获取过期设置（和前面说的 jsonSchema validator 一样，相关信息存储在 `_mdb_catalog` 元数据表中）。

由于时序表采用列存存储数据，如果按行进行 TTL 淘汰，这些按行删除的动作势必会转换成大量对 bucket 的 update 操作，导致性能下降。

针对这些问题，时序表的 TTL 有以下性能优化：

1. 并不会每条数据单独删除，而是按照 bucket 来删除。具体来说，`safeExpirationDate` 函数中指定的淘汰规则是 `Date_t::now() - Seconds(expireAfterSeconds) - bucketMaxSpan`，能保证 bucket 中的全部数据都过期之后，整 bucket 删除；
2. 时序表底层是 _id 组织的聚簇表，其中 _id 就是执行 TTL 时用于比较的时间字段，因此比走普通的 INDEX_SCAN 删除要快。

## 2.3 读写流程

时序表的读写都是通过视图进行的，不会直接操作底层的 `system.buckets.*` 表。

内核会将用户对视图的读写命令，转换成对底层表的读写操作。下面分别进行讨论。

### 2.3.1 查询

转换为聚合 + 下推优化：

```javascript
// 数据格式：
// 底层桶文档 system.buckets.weather（V2，sensorId=1 的 60 条分钟级数据）
{
  _id: ObjectId("68F0A8C0..."),            // 时间部分 = 10:00 向下取整到分钟（granularity=seconds）
  control: { version: 2,
             min: { timestamp: ISODate("...T10:00"), temp: 21.1 },
             max: { timestamp: ISODate("...T10:59"), temp: 22.8 },
             count: 60 },
  meta: { sensorId: 1 },
  data: { timestamp: BinData(7, <BSONColumn>),   // 60 个递增时间戳，DoD 后几乎全 0
          temp:      BinData(7, <BSONColumn>) }
}

// 用户查询
db.weather.find({ sensorId: 1,
                  timestamp: { $gte: ISODate("...T10:30") },
                  temp: { $gt: 22 } }).sort({ timestamp: 1 })

// 实际下发到 system.buckets.weather 的等价管道
[
  { $match: { $and: [                       // ---- loose：先在桶层缩小范围（走默认复合索引）
      { meta: 1 },
      { control.max.timestamp: { $gte: T10:30 } },          // 桶最新数据 >= 10:30 才可能含命中点
      { control.min.timestamp: { $gte: T10:30 - 3600s } },  // 放宽 bucketMaxSpan（秒级粒度=1h）
      { _id: { $gte: MinOID(T09:30) } },                    // OID 范围 → 聚簇扫描可用
      { control.max.temp: { $gt: 22 } }                     // 测量字段 loose（桶内最大 temp）
  ] } },
  { $_internalUnpackBucket: {
      timeField: "timestamp", metaField: "sensorId",
      bucketMaxSpanSeconds: 3600,
      include: ["temp"],                                   // 列裁剪：只要 temp 列（依赖分析得出）
      wholeBucketFilter: { control.min.timestamp: { $gte: T10:30 }, ... },  // tight
      eventFilter: { timestamp: { $gte: T10:30 }, temp: { $gt: 22 } } } },  // 逐条残余
  { $sort: { timestamp: 1 } }                              // 有序桶可利用内部有序性
]
```

### 2.3.2 插入

重定向到 bucket 集合并分桶。转换/优化流程：

1. `insertIntoBucketCatalog()` 逐条调用 `timeseries::attemptInsertIntoBucket()`：校验 timeField 存在且为 Date、提取/规范化 metaField（嵌套对象按字典序归一化，便于分桶），交给 `BucketCatalog` 按（metadata、时间范围、桶大小限制）定位目标桶，产出 `WriteBatch`；
2. 提交时按桶写存储，且把用户 insert 隐式转换成对 bucket 集合的 insert 或 update：
   - 桶的第一批数据 → `performTimeseriesInsert`：对 `system.buckets.weather` 插入一条 bucket 文档；
   - 后续数据 → `makeTimeseriesUpdateOp` / `makeTimeseriesCompressedDiffUpdateOp`：对已有 bucket 文档做 delta 更新（**DocDiff + BSONColumn 追加**），而非重写整文档，大幅减小写放大与 oplog 体积；
   - 另外一个 bucket 文档的数据量比较大（可达 1000 条数据，或者 125KB 级别），如果按照 WiredTiger 常规的 update 方式，底层的 MVCC 链上会有很多的“超大版本”，导致内存压力急剧增加。为此，WiredTiger 提供了一种**将 MVCC 版本 Delta 化的方式**：对 >1KB、改动 ≤16 处、≤10% 的文档（时序表完美满足），MongoDB 自动算出 delta 并走 `cursor->modify`（参考 `WiredTigerRecordStore::doUpdateRecord` 函数）。WT_MODIFY 在 update chain（WT_UPDATE 结构）里只挂 `{offset, size, data}` 修改向量，不复制整份新文档；需要旧版本可见性的读者由磁盘/内存 base value 逆向应用 delta 链重建；
3. 其他优化：多客户端写同桶合并（`canCombineTimeseriesInsertWithOtherClients`）、DuplicateKey 自动重试重开桶、桶关闭时即时压缩为 v2、无序写的并发提交。

### 2.3.3 更新和删除

时序表对 update 操作有严格的限制，只能更新 meta 部分，不能更新 measurement，参考[官方文档](https://www.mongodb.com/zh-cn/docs/manual/core/timeseries/timeseries-limitations/?interface=driver&language=python#updates)的限制说明。

否则，会执行报错：

```text
"Cannot perform an update on a time-series collection which updates a field that is not the metaField 'tags'"
```

而且更新操作必须指定 multi = true，即使用 updateMany，否则会报错：

```text
"Cannot perform a non-multi update on a time-series collection"
```

从执行计划的角度来看，如果是按照 metaField 更新和删除，会比较简单。但是如果是指定 measurement 进行删除，**由于涉及的数据已经打包到了列存中，会涉及到拆包和重新封包的操作**，会比较麻烦。

对后一种场景来说：

1. 按**用户谓词逐 measurement 过滤**，分成 `unchanged` 与 `matched`；
2. `unchanged` 非空 → 对原桶（同 `_id`）生成替换/更新（repack）；为空 → 整桶删除。谓词能整桶命中时直接对桶文档执行，跳过解包；
3. 原子性保证：原桶修改 + 新桶插入在**单个 WriteUnitOfWork**  事务块内完成，且把多条 oplog 打包成一条 `applyOps` 复制，secondary 要么全应用要么全回滚。

需要说明的是，如果在配置文件中开启了 `featureFlagTimeseriesUpdatesSupport: true`（默认为 false），则能执行 UpdateOne 操作，并解除官方文档中对于只能更新 metaField 的限制。    
比如下面的操作，修改非 metaField 字段：
```
mymongo80:PRIMARY> db.ts.find()
{ "ts" : ISODate("2026-10-02T00:07:05.687Z"), "node" : "node1", "_id" : ObjectId("6abef5a9a44ca4e62e419679"), "d" : 5 }
{ "ts" : ISODate("2026-10-02T00:07:11.993Z"), "node" : "node1", "_id" : ObjectId("6abef5afa44ca4e62e41967b"), "d" : 6 }
mymongo80:PRIMARY> db.ts.updateOne({"ts" : ISODate("2026-10-02T00:07:11.993Z")}, {$set: {d:7}})
{ "acknowledged" : true, "matchedCount" : 1, "modifiedCount" : 1 }
mymongo80:PRIMARY> db.ts.find()
{ "ts" : ISODate("2026-10-02T00:07:05.687Z"), "node" : "node1", "_id" : ObjectId("6abef5a9a44ca4e62e419679"), "d" : 5 }
{ "ts" : ISODate("2026-10-02T00:07:11.993Z"), "node" : "node1", "_id" : ObjectId("6abef5afa44ca4e62e41967b"), "d" : 7 }
```
对于这种 UpdateOne 的场景，操作在 mongod 侧逐桶执行：
1. 解包当前桶 → 按**用户谓词逐 measurement 过滤**，分成 `unchanged` 与 `matched`；
2. update：对 matched 应用用户更新算子得到 `modified`，重新分桶插入；
3. **原子性**：原桶修改 + 新桶插入在**单个 WriteUnitOfWork**内完成，且把多条 oplog 打包成一条 `applyOps` 复制，secondary 要么全应用要么全回滚；

# 3. 存储方式

## 3.1 行组的列存压缩

MongoDB 时序表底层采用行组的方式进行列存压缩。一般来说，当 bucket 凑集 1000 条，或者 125KB 之后，将这个行组的数据按照列进行组织，每个列根据类型选取对应的压缩算法进行压缩。压缩后这个行组的大小急剧变小，然后作为一个“大行”存储到 WiredTiger 存储引擎中。

在 5.0 内核初次引入时序表功能时，只是将行组中的列聚合在一起采用 Object 存储，并没有压缩（下文中的 V1 版本），此后引入了压缩算法，并采用 BinData 格式存储（下文中的 V2 版本），并在 8.0 作为了默认格式。

区别如下：

```javascript
V1（未压缩，行式子文档，5.0-7.0 旧格式，8.0 起不再新建）:
{
  _id: ObjectId(<control.min.time 同时刻>),     # 桶按 _id 时间聚簇
  control: { version: 1,
             min: { timestamp: T0, temp: 21.5, ... },
             max: { timestamp: T9, temp: 22.3, ... },
             closed: <bool> },
  meta: { sensorId: 1, ... },                   # 归一化后的公共 meta
  data: { timestamp: { "0": T0, "1": T1, ... }, # "0"/"1"... 是字符串化的行号
          temp:      { "0": 21.5, "2": 21.9, ... } }   # 缺失行可跳过(skip)
}

V2/V3（压缩，BSONColumn 列存，8.0 起新桶默认 V2）:
{
  _id: ObjectId(...),
  control: { version: 2, min: {...}, max: {...}, count: 1000 },
  meta: { ... },
  data: { timestamp: BinData(7, <BSONColumn>),  # BinDataType 7
          temp:      BinData(7, <BSONColumn>) }
}
```

- V2 = 压缩且按时间有序（读性能好）；V3 = 压缩但乱序（同一桶收到乱序写入时由 V2 提升，保写吞吐）；
- 桶中 measurement 数量以 `data.<timeField>` 的元素数为准（v1）/ control.count（v2/v3）；非时间列可有 skip 但不能多于时间列；
- 从 5.2 开始引入压缩，参考[官方文档](https://www.mongodb.com/zh-cn/docs/manual/core/timeseries/timeseries-compression/)。

几个版本的区别对比如下：

| 维度 | V1（未压缩） | V2（压缩+有序） | V3（压缩+乱序） |
| :-- | :-- | :-- | :-- |
| `data.<field>` 形态 | 子文档 `{"0": v, "1": v, ...}`（每个值带类型标签+行号字符串） | BSONColumn BinData(7) | BSONColumn BinData(7) |
| 时间有序性 | 否，根据数据的到达顺序插入 | 是 | 否（至少 1 条乱序） |
| 跨值压缩 | 无（仅依赖存储层块压缩器） | Delta / Delta-of-Delta / Simple-8b / interleaved | 同 V2 |
| 追加写方式 | 子文档 insert-section diff | append-only 列构建器 + binary DocDiff | 同 V2 |
| 查询可利用有序性 | 否 | 是（提前终止、紧谓词、last-point 优化） | 否 |
| 引入/默认情况 | 5.0 起的原始格式，8.0 起不再新建 | 6.x 起关桶时压缩落盘；**8.0 起全程默认** | 8.0 乱序写路径 |

## 3.2 时序表组织架构

时序表的组织架构如下图所示，主要包括以下几个部分：

1. 可读写视图：用于请求转换；
2. BucketCatalog：用内存索引换磁盘查找、用批量合并换单条写放大。
   - 定位：O(1) 找到该写进哪个 bucket；
   - 写合并：把并发写聚成批量提交（核心价值）；
   - rollover 决策：bucket 什么时候“写满”；
3. 一个 btree 组织的行存表，按照 _id 为 key 组织，以 bucket 作为存储单元，内部使用列存压缩，对应到表中就是一行比较大的数据。

# 4. 牺牲的功能：ChangeStream/CDC 和事务

时序数据库由于其特有的存储方式，带来了很多的使用限制。完整的限制列表可以参考[官方文档](https://www.mongodb.com/zh-cn/docs/manual/core/timeseries/timeseries-limitations/?interface=mongosh)。

个人认为，影响最大的，就是不支持 ChangeStream 和事务功能。

## 4.1 对 ChangeStream 的影响

对时序视图的插入操作，最终会转换为对底层 `system.buckets` 表的 update 操作。oplog 中存储的，是对列存压缩二进制的直接修改，举例如下：

```javascript
{
        "op" : "u",
        "ns" : "ts.system.buckets.cpu",
        "ui" : UUID("afb4e422-16c4-4b2b-9c76-9fa55ec26823"),
        "o" : {    // 通过 diff 字段，记录了 update 操作的详细信息
                "$v" : 2,
                "diff" : {
                        "scontrol" : {
                                "u" : {
                                        "count" : 2
                                },
                                "smax" : {  // 表示修改了 control.max
                                        "u" : {
                                                "_id" : ObjectId("6aaa34033235af6f0c78cc7d"),
                                                "timestamp" : ISODate("2026-09-16T06:15:31.052Z"),
                                                "cpu_usage" : 78
                                        }
                                }
                        },
                        "sdata" : {
                                "b" : {
                                        "timestamp" : {
                                                "o" : 10,   // 修改的位置： offset
                                                "d" : BinData(0,"gM4XBAAAAAAAAA==")  // 修改后的值
                                        },
                                        "_id" : {
                                                "o" : 14,
                                                "d" : BinData(0,"gE4g4R8AAAAAAA==")
                                        },
                                        "cpu_usage" : {
                                                "o" : 10,
                                                "d" : BinData(0,"kC4AAAAAAAAAAA==")
                                        }
                                }
                        }
                }
        },
        "o2" : {
                "_id" : ObjectId("6aaa33e4133e32f654cc680a")
        },
        "ts" : Timestamp(1789539331, 1),
        "t" : NumberLong(1),
        "v" : NumberLong(2),
        "wall" : ISODate("2026-09-16T06:15:31.052Z")
}
```

为了在列式压缩下尽量提升复制性能，对 `o` 字段进行了扩展，通过存储 oplog diff 的方式，减少 oplog 大小（不需要用 `$set` 记录修改后的全量值），并提升 apply 性能（直接应用，不需要解压和重新压缩）。

但如果要支持 ChangeStream，**需要反解出对应的二进制的那段区间具体对应的什么内容，理论上流程会非常复杂，性能无法保障。**

## 4.2 对事务的影响

和其他基于行存的 OLTP 数据库一样，MongoDB 中的每一行数据，会有对应的元数据信息（插入/删除这个版本的 transactionId 和 timestamp 等）。通过这些元数据信息，MongoDB 能够很好的支持事务（包括 MVCC 隔离，事务 commit/abort/prepare 等）。

使用时序表之后，写入同一个 bucket 的多个插入请求，会进行合并，最终由 leader 事务完成存储引擎插入，其他事务会等待 leader 事务完成，示意图如下：

<img width="720" height="817" alt="image (1)" src="https://github.com/user-attachments/assets/cd0aacec-7971-4694-9cd6-5796f52ad1fe" />
</p>

这种代理提交的方式，摧毁了事务边界，导致每个独立的事务无法单独回滚。

因此，MongoDB [官方文档](https://www.mongodb.com/zh-cn/docs/manual/core/timeseries/timeseries-limitations/?interface=driver&language=python#transactions)中，明确说明了不要将时序表的写入请求放到事务块中。

不过使用 8.0 内核版本实测发现，有部分写入操作还是能在事务中的，测试脚本和执行结果参考附录B, 执行结果总结如下：
|场景|结果|证据|
|:--|:--|:--|
|事务内`insertOne`|拒绝 ，code 263|Cannot insert into a time-series collection in a multi-document transaction|
|事务内`updateMany` （multi）|拒绝 ，code 263|Cannot perform a multi update inside of a multi-document transaction...|
|事务内`deleteMany` （multi）|拒绝 ，code 263|Cannot perform a multi delete inside of a multi-document transaction...|
|事务内`updateOne`|允许|提交后生效（temp=55，nModified=1），事务内能读到自己的写<br>前提是在**配置文件中设置 featureFlagTimeseriesUpdatesSupport 为 true**，这个参数默认是 false|
|事务内`deleteOne`|允许|提交后 S2 由 2 → 1|
|事务内`findAndModify`|允许|提交后 temp=66|
|事务内`updateOne` +`abortTransaction`|正确回滚|事务内见 77 → abort 后回到 23|
|事务外`updateMany` /`deleteMany` （可重试写路径）|允许|3 条全改 88；精确删 1 条|



不过有一些 OLTP 行存数据库能支持完整的事务，比如 PostgreSQL 生态的 TimescaleDB，参考后文的描述。

也有一些时序数据库干脆放弃了事务，比如 InfluxDB 和 ClickHouse。

# 5. 横向对比

本节参考 Tiger Data 官方白皮书 [Tiger Data architecture for real-time analytics](https://www.tigerdata.com/docs/learn/deep-dive/whitepaper)，总结 TimescaleDB 的设计思想与核心特点，并与 MongoDB 时序表做简要对比。

## 5.1 设计思想

TimescaleDB 的定位是"为实时分析而生的应用数据库"，设计思想可以概括为三点：

1. **站在 PostgreSQL 的肩膀上做扩展，而非另起炉灶**：以扩展形式实现，完整继承 SQL（含 JOIN、窗口函数）、ACID 事务、MVCC 等能力，用户可以沿用熟悉的工具链；
2. **自动分区 + 行列混合存储**：hypertable（超表）自动按时间切成 chunk，hypercore 让行存（热数据/事务）与列存（历史数据/分析）共存于一个库，同时追求高吞吐写入与低延迟分析；
3. **用预计算换运行时开销**：continuous aggregates（增量维护的物化视图）和 hyperfunctions（部分聚合状态）把昂贵的计算从每次查询挪到数据写入后的异步环节。

## 5.2 核心特点

1. **Hypertable 自动分区**：每个 chunk 有独立的索引与存储，写入只落在最近的少量小 chunk 上（索引小、缓存友好、vacuum 开销低）；查询基于 chunk 的 min/max 元数据裁剪，数据保留可以整 chunk 丢弃；
2. **行列混合 + 高压缩**：最新数据驻留行存，后台按批（每列最多 1000 个值）压缩为列存，列级使用 RLE、delta、Gorilla 等算法，压缩率最高可达 95%；batch 内用 SEGMENTBY 聚簇相关行、ORDERBY 按时间排序，配合 SIMD 向量化执行加速过滤和聚合；
3. **完整可变性**：对压缩数据的 update/delete 不改写列存本体，而是把受影响的 batch 解压暂存到临时行存 chunk，修改立即可见，再由后台重新压缩；
4. **Continuous aggregates**：增量维护按时间分桶的物化视图，只刷新失效的时间区间，支持实时模式（合并预计算结果与最新原始数据）与层级 rollup（分钟→小时→天）。

## 5.3 与 MongoDB 时序表的主要差异

有趣的是，两者在行组大小上高度一致（MongoDB bucket 上限 1000 条 measurement，TimescaleDB batch 每列最多 1000 个值），但设计取向差异明显：

| 维度 | TimescaleDB | MongoDB 时序表 |
| :-- | :-- | :-- |
| 架构定位 | PG 扩展，完整 SQL + ACID 事务 + JOIN | 视图 + `system.buckets`，事务与更新受限 |
| 分桶维度 | 仅按时间切 chunk，一个 chunk 含所有设备的数据 | 按（metaField, 时间）双重分桶，一桶只含单个设备 |
| 冷热存储 | 行存/列存混合，热数据行存可变 | 桶关闭后即列存压缩，写入直接面向压缩数据（支持边写边压） |
| 更新/删除 | 全可变（行存暂存 + 后台重压缩） | 仅可更新 metaField，改 measurement 需拆桶重打包（并且需要先手动改 featureFlagTimeseriesUpdatesSupport 配置并重启） |
| 预计算 | continuous aggregates 增量物化 + 部分聚合 | 聚合管道实时计算 / on-demand 物化视图（全量重建） |

几点展开：

1. **生态与事务能力**：TimescaleDB 作为 PG 扩展天然具备完整事务、MVCC 与 JOIN（正好对应本文第 4 节 MongoDB 时序表不支持多文档事务、限制 update 的痛点）；MongoDB 则选择牺牲这些换取写吞吐与存储效率；
2. **分桶粒度**：TimescaleDB 的时间 chunk 内含所有设备，靠 SEGMENTBY 在 batch 内再聚簇；MongoDB 把设备 ID 提升为一级分桶键，设备级过滤在桶层即可完成（走 `meta + control.min/max.timestamp` 索引），但海量设备会产生大量小桶，削弱列存压缩收益；
3. **可变性的实现路径**：TimescaleDB 用"行存暂存 + 后台重压缩"统一解决增删改；MongoDB 选择写入即压缩（BucketCatalog 攒批 + DocDiff 追加），写吞吐更高，代价是删改必须拆桶重打包；
4. **预计算体系**：continuous aggregates 是内核原生的增量物化视图，配合 partial aggregation 可低成本做多级 percentile 等 rollup；MongoDB 时序表没有对应机制，预聚合需用户自行用 `$merge` 落地，且不支持增量刷新。

总体而言，TimescaleDB 追求"一个数据库同时服务 OLTP 与实时分析"，功能完整、分析能力强；MongoDB 时序表更像是"在通用文档数据库上以视图 + 列存桶实现的时序加速层"，实现轻量、与 MongoDB 生态无缝，但功能上做出了明显妥协。

配置文件中设置 featureFlagTimeseriesUpdatesSupport 为 true，这个参数默认是 false:

```
setParameter:
```

测试脚本：
```
// ts_txn_test.js — 验证时序集合（time-series）在多文档事务中的支持矩阵
// 服务端启动参数: --setParameter featureFlagTimeseriesUpdatesSupport=true
// 矩阵（源自 write_ops_exec.cpp 的 uassert）：
//   事务内 insertOne        -> 拒绝 OperationNotSupportedInTransaction (code 263)
//   事务内 multi update     -> 拒绝 263
//   事务内 multi delete     -> 拒绝 263
//   事务内 updateOne        -> 允许（direct write 路径，需 updates feature flag）
//   事务内 deleteOne        -> 允许（deletes feature flag 默认开）
//   事务内 findAndModify    -> 允许
//   事务内 updateOne + abort -> 可回滚
//   事务外 multi update/delete（可重试写）-> 允许

var testDb = db.getSiblingDB('ts_txn_test');
testDb.dropDatabase();
testDb.createCollection('weather', { timeseries: { timeField: 'ts', metaField: 'sensorId' } });
var coll = testDb.weather;

var T = function (s) { return new Date('2026-09-24T' + s + ':00.000Z'); };

coll.insertMany([
  { ts: T('10:00'), sensorId: 'S1', temp: 21 },
  { ts: T('10:01'), sensorId: 'S1', temp: 22 },
  { ts: T('10:02'), sensorId: 'S1', temp: 23 },
  { ts: T('10:00'), sensorId: 'S2', temp: 31 },
  { ts: T('10:01'), sensorId: 'S2', temp: 32 }
]);
print('SETUP | measurements=' + coll.count() + ' (S1=3, S2=2)');
print('--------------------------------------------------------------');

var pass = 0, fail = 0;
function report(ok, name, detail) {
  if (ok) { pass++; print('PASS | ' + name + (detail ? ' | ' + detail : '')); }
  else    { fail++; print('FAIL | ' + name + (detail ? ' | ' + detail : '')); }
}
// 期望失败：err.code 或 err.codeName 任一匹配即可（legacy shell 只有 code）
function expectFail(name, expectedCode, expectedName, fn) {
  var err = null;
  try { fn(); } catch (e) { err = e; }
  if (!err) { report(false, name, '期望失败(' + expectedName + '/' + expectedCode + ')但成功了'); return; }
  var codeStr = String(err.code !== undefined ? err.code : (err.codeName || '?'));
  var hit = (err.code !== undefined && err.code === expectedCode) ||
            (err.codeName !== undefined && err.codeName === expectedName);
  report(hit, name, 'code=' + codeStr + ' | ' + String(err.message || err.errmsg || err).substring(0, 95));
}
function expectWork(name, fn) {
  try { var r = fn(); report(true, name, 'ok'); return r; }
  catch (e) { report(false, name, String(e.message || e.errmsg || e).substring(0, 120)); return null; }
}
function nModified(r) { return r ? (r.nModified !== undefined ? r.nModified : r.modifiedCount) : -1; }
function nDeleted(r) { return r ? (r.deletedCount !== undefined ? r.deletedCount : (r.n !== undefined ? r.n : -1)) : -1; }
function newTxn() {
  var s = db.getMongo().startSession();
  s.startTransaction({ readConcern: { level: 'snapshot' }, writeConcern: { w: 'majority' } });
  return s;
}

// ---- T1: 事务内 insert ----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  expectFail('T1 事务内 insertOne', 263, 'OperationNotSupportedInTransaction', function () {
    c.insertOne({ ts: T('10:05'), sensorId: 'S1', temp: 99 });
  });
  s.abortTransaction(); s.endSession();
  report(coll.count({ temp: 99 }) === 0, 'T1b 回滚后无残留', 'temp99=' + coll.count({ temp: 99 }));
})();

// ---- T2: 事务内 multi update ----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  expectFail('T2 事务内 updateMany(multi:true)', 263, 'OperationNotSupportedInTransaction', function () {
    c.updateMany({ sensorId: 'S1' }, { $set: { temp: 90 } });
  });
  s.abortTransaction(); s.endSession();
  report(coll.count({ temp: 90 }) === 0, 'T2b 无残留', 'temp90=' + coll.count({ temp: 90 }));
})();

// ---- T3: 事务内 multi delete ----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  expectFail('T3 事务内 deleteMany(multi:true)', 263, 'OperationNotSupportedInTransaction', function () {
    c.deleteMany({ sensorId: 'S1' });
  });
  s.abortTransaction(); s.endSession();
  report(coll.count() === 5, 'T3b 计数不变', 'count=' + coll.count());
})();

// ---- T4: 事务内 updateOne（singleton direct write）----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  var r = expectWork('T4 事务内 updateOne', function () {
    return c.updateOne({ sensorId: 'S1', ts: T('10:01') }, { $set: { temp: 55 } });
  });
  var inTxn = expectWork('T4b 事务内读自己的写', function () { return c.findOne({ sensorId: 'S1', ts: T('10:01') }); });
  s.commitTransaction(); s.endSession();
  var after = coll.findOne({ sensorId: 'S1', ts: T('10:01') });
  report(after && after.temp === 55 && nModified(r) === 1 && inTxn && inTxn.temp === 55,
         'T4c 提交后生效(55)', 'temp=' + (after && after.temp) + ' nModified=' + nModified(r));
})();

// ---- T5: 事务内 deleteOne ----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  var r = expectWork('T5 事务内 deleteOne', function () {
    return c.deleteOne({ sensorId: 'S2', ts: T('10:00') });
  });
  s.commitTransaction(); s.endSession();
  report(coll.count({ sensorId: 'S2' }) === 1 && nDeleted(r) === 1,
         'T5b 提交后 S2 剩 1 条', 'S2=' + coll.count({ sensorId: 'S2' }) + ' n=' + nDeleted(r));
})();

// ---- T6: 事务内 findAndModify ----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  var doc = expectWork('T6 事务内 findAndModify', function () {
    return c.findAndModify({ query: { sensorId: 'S2', ts: T('10:01') }, update: { $set: { temp: 66 } }, new: true });
  });
  s.commitTransaction(); s.endSession();
  var after = coll.findOne({ sensorId: 'S2', ts: T('10:01') });
  report(after && after.temp === 66 && doc && doc.temp === 66, 'T6b 提交后 temp=66', 'temp=' + (after && after.temp));
})();

// ---- T7: 事务内 updateOne + abort（回滚语义）----
(function () {
  var s = newTxn();
  var c = s.getDatabase('ts_txn_test').weather;
  expectWork('T7a 事务内 updateOne(temp:77)', function () {
    return c.updateOne({ sensorId: 'S1', ts: T('10:02') }, { $set: { temp: 77 } });
  });
  var inTxn = expectWork('T7b 事务内已见 77', function () { return c.findOne({ sensorId: 'S1', ts: T('10:02') }); });
  s.abortTransaction(); s.endSession();
  var after = coll.findOne({ sensorId: 'S1', ts: T('10:02') });
  report(after && after.temp === 23 && inTxn && inTxn.temp === 77,
         'T7c abort 后回滚为 23', 'temp=' + (after && after.temp));
})();

// ---- T8: 事务外 multi update / delete（可重试写路径）----
(function () {
  var r = expectWork('T8a 事务外 updateMany(可重试写)', function () {
    return coll.updateMany({ sensorId: 'S1' }, { $set: { temp: 88 } });
  });
  report(nModified(r) === 3 && coll.count({ sensorId: 'S1', temp: 88 }) === 3,
         'T8b S1 全部改为 88', 'nModified=' + nModified(r));
  var d = expectWork('T8c 事务外 deleteMany(可重试写)', function () {
    return coll.deleteMany({ sensorId: 'S1', ts: T('10:00') });
  });
  report(nDeleted(d) === 1 && coll.count({ sensorId: 'S1' }) === 2, 'T8d 删除 S1@10:00 一条', '剩 S1=' + coll.count({ sensorId: 'S1' }) + ' n=' + nDeleted(d));
})();

print('--------------------------------------------------------------');
print('SUMMARY | pass=' + pass + ' fail=' + fail + ' | 最终 total=' + coll.count());
```
